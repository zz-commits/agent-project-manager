# V1 core 协议决定

状态：用户已采纳，2026-10-08。本文记录本次会话采纳的建议及为使其可实施而补齐的规则，不是交付证明。

## 首轮范围与验收

以本项目为真实试点，建立校验、状态查询、重建、Claim 和交接五个 Feature。首轮实现 Phase 1–3；测试命令执行、Evidence 导入、Git/MR 交付接入仍属于 Phase 4。人工维护事实后运行只读校验，首轮不扩大到完整 Feature/Requirement 写入 API。

Python 3.12+，uv 与锁文件，argparse，ruamel.yaml（YAML 1.2），JSON Schema Draft 2020-12，pytest。结构规则只保存在 JSON Schema；跨模型规则在核心校验器。filelock 提供本地项目写锁。Linux 为本次验证平台；macOS 为设计目标，Windows 不声明已验证。先本地安装，不自动向包仓库发布。

## 标识、输入与路径

- managed 模式实体 ID 使用类型前缀与 UUIDv4，Source 也遵循此规则；example 模式保留 EXAMPLE ID。AC/Check ID 在单个 Feature 内唯一。
- version=1；未知字段拒绝，扩展只允许 extensions 对象。YAML 只接受单个文档与安全标准标签，拒绝重复键。RFC3339 字符串必须有时区。时间写入使用 UTC，查询可接受显式评估时间。
- 路径使用仓库相对 POSIX 形式；拒绝绝对路径、反斜杠、父目录跳转及符号链接越界。Claim 支持文件、目录（末尾 /）、根目录 . 和目录下的 /**；不支持其他 glob。feature Claim 覆盖同一 Feature 以及其已知 component 路径；范围不明确时保守报告可能冲突。
- confirmed Requirement 如引用 inferred Source，须有 confirmation={reviewer, note, confirmed_at}，不能自动升级来源权威。

## subject 与 Check 定义

干净代码树使用完整 Commit SHA；代码变更时使用 working_tree subject，value 为 sha256: 加摘要。指纹包括 HEAD 与 Git tracked/非忽略 untracked 文件的路径、类型、执行位和内容；包含删除标记，按路径排序。排除根 .git、.project、虚拟环境、缓存和构建输出；不能任意排除源代码。排除元数据避免写 Evidence 自身使代码指纹变化。被测代码有变化时必须重新设置 Feature.subject，查询同时比较当前代码 subject，避免沿用旧结果。

Check 定义摘要为 UTF-8 canonical JSON（sort_keys=true，紧凑 separators，ensure_ascii=false）的 SHA-256；输入为 {id, acceptance_ref, required, command_ref, command}，command 是 Project.commands 的对应定义或 null。activity 与 evidence_refs 不影响摘要。用于验证的 Evidence 增加 check_digest；方法变更后旧证据 stale。自动测试的实际 argv/cwd 必须与 Check 对应命令一致，否则未验证。历史 example/not_verified 记录可以缺少摘要，但不能产生 PASS。

## 证据与状态

- 所有 required AC 的 required Check 都有效通过才 passed；可选 AC/Check 的失败或阻塞只作为独立信息，不影响 required 汇总。
- supersedes 只允许同一 Feature/Check，不能成环。未裁决的有效 passed/failed 冲突使 verification=blocked；生命周期不能超过 verifying。失效、缺失、not_verified、产物过期均不算 PASS。
- 自动测试 passed 必须有命令、exit_code=0 与可读取的非空产物列表；不把任意退出码 0 泛化到其他 Check。人工 passed 必须有 reviewer、note、可检查产物，且 Project 允许人工证据。
- 本地文件产物要求存在；有 sha256 时必须匹配。首版不下载远程产物；仅 URL 的证据保持未验证并解释原因。Evidence 新鲜度由 AC/需求版本、subject、Check 摘要共同决定。
- 默认交付门槛仍为 merged；Commit 只记录 committed。首版只评估可核实的已有人工交付 Evidence，不连接远程 MR API。kind/state 不相容拒绝输入。
- 没有 Feature 的空项目合法；有 Feature 则必须有 required AC 和对应 required Check。Phase 2 可以评估 Phase 4 尚未支持写入的事实。

## 写入、恢复与 bootstrap

使用项目级短时写锁，并在锁内重新读入事实、检查 revision、校验完整候选项目。多文件事务先持久化恢复日志，再逐文件原子替换；全部落盘后清理日志。日志位于 .project/transactions，与可删除 cache 分开。发现未完成日志时禁止新写入，doctor 返回阻塞；doctor --recover 在锁内按日志完成已验证事务，保留可重复恢复能力。rebuild 采用同一机制，事实文件不回写。

Handoff 先准备并校验，和 Run 终态一起提交；Run 仍为 active 时 Claim 继续有效。completed 不表示 Feature 已验收，aborted 要记录理由。有 remaining/blockers 的终态必须关联 Handoff；Handoff 内容须反映同一次 Run 的遗留事项。

原始虚构记录保留在 examples/design/.project，连同其设计基线文档；根 .project 为真实项目。CLI bootstrap 期间手工登记真实 Run 与 Claim，校验器出现后立即校验。后续优先使用 CLI，手工维护须运行 doctor。本次不自动 commit、push、发布或部署。
